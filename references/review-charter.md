# 复核范围卡与权威基准

> 本文件是每次复核的第一个上下文入口。目标是冻结"审什么、以什么为准、审到什么程度、哪些事项未覆盖"，避免后续凭经验扩围、换口径或静默降级。

## 一、一次性确认范围

先扫描用户已提供的信息，只询问缺失且会改变结论的事项。建议使用以下范围卡：

```yaml
review_id: FR-YYYYMMDD-001
task_type: initial | quick | continuation | special
depth: programmatic | full
review_position: independent | project_team | intermediary
documents:
  - id: M1
    name: 清洁版问询回复
    role: primary
    version: 修订稿
    sha256: ""
    modified_at: ""
report_periods: ["2023", "2024", "2025", "2026H1"]
latest_period: "2026H1"
data_cutoff: "2026-06-30"
source_access_date: "2026-09-25"
markup_convention: kai_bold  # 修订标注体例：kai_bold（楷体加粗）| track_changes（修订模式）| none（无标注，用上期 diff）
extension_review: true
working_papers_available: true
external_check: false  # 一般外部核查；触发上市公司定期报告取证专项时设为 true，并限定授权范围
prior_findings_available: true
authority_baseline:
  - data_type: 报告期实际财务数据
    source_ref: SRC-0001   # 证据台账中的 SRC- ID
    note: 以签署版审计报告为最终权威
not_in_scope:
  - 图片和文本框内文字
  - 未提供的底稿
```

范围卡必须写入 `manifest.json`，后续步骤不得静默修改。确需变更时记录变更原因、时间和影响范围。

**已授权的上市公司定期报告取证**：复核对象包含上市公司相关信息，而用户未提供对应年度报告、半年度报告或季度报告时，自动联网下载官方完整披露文件作为底稿，不再询问是否允许外部取证。按主体、证券代码、期间及事项列出所需报告，将下载文件登记为 `external` 来源，并为所核事项建立 `authority_baseline` 映射；启用 `external_check` 时，在范围卡及来源说明中明确仅启用该专项，不据此扩展工商、同业或其他核查。下载报告缺少某项信息时，只记录相应缺口，不将报告整体视为覆盖全部上市公司信息。

## 二、任务类型

| 类型 | 目标 | 最低要求 |
|---|---|---|
| `initial` 初核 | 首次完整复核 | 全部适用维度 + 元审计 |
| `quick` 快筛 | 过程性排查 | 程序化基线 + 数值索引；明确不能冒充全量 |
| `continuation` 续核 | 修订后逐条闭环 | 原 finding 状态 + 回归检查 |
| `special` 专项 | 只查一个维度 | 专项规则 + 覆盖限制 |

## 三、权威基准：一个基准 + 五个核对维度

### 1. 一个基准

所有申报文件数据必须与对应唯一权威来源比对。默认分层如下，用户或项目底稿另有明确口径时以用户确认口径为准：

| 数据类型 | 默认权威来源 |
|---|---|
| 报告期实际财务数据 | 审定财务报表、财务报表附注、备考审阅报告 |
| 评估与预测数据 | 评估说明、评估明细、预测期利润表、折现率和资本性支出底稿 |
| 历史沿革、股权结构、实控人 | 法律意见书或补充法律意见书 |
| 土地房屋、知识产权、资质、重大合同 | 法律意见书或补充法律意见书 |
| 上市公司公开定期报告信息 | 对应主体、期间及披露版本的完整年度报告、半年度报告或季度报告；未提供时按已授权专项从官方来源下载 |
| 公开监管信息 | 法规原文、交易所/监管公告、官方披露页面 |
| 公司业务事实 | 项目底稿、合同、访谈、工商与公开披露，按证据层级判断 |

**权威基准结构化**：上表口径必须在 `manifest.json` 的 `authority_baseline` 中逐条记录为 `{data_type, source_ref, note}` 映射（`source_ref` 为证据台账中的 `SRC-` ID），不得只用自由文本；校验脚本据此核对 CONFIRMED 数值 finding 是否挂到已声明的权威来源。

**旧格式迁移**：历史项目若已用字符串数组格式的 `authority_baseline`（如 `authority_baseline: ["以签署版审计报告为最终权威"]`），schema 仍兼容接受、校验不报错，但校验脚本会逐条发出迁移警告；字符串条目没有 `source_ref`，不参与 CONFIRMED 数值 finding 的权威来源挂载核对（可能导致该核对整体不触发），因此续核历史项目时应先把字符串条目迁移为 `{data_type, source_ref, note}` 对象格式，再开展本轮复核。

来源角色必须标注为：

- `working_paper`：TB、审计报告、评估说明、法律意见书、Excel 计算底稿；
- `filing`：主文件或明确的申报文件组成部分；
- `comparison`：用户明确指定的其他申报文件；
- `external`：法规、监管、交易所、公司官方或公开来源；
- `internal_note`：项目组说明、会议记录或内部确认口径。

主文件组成部分不得误称为对照组或底稿。

### 2. 五个核对维度

1. **表内勾稽**：合计、分项和、占比、增长率、完成率、单价、毛利率、率×基数、会计恒等式。
2. **表外一致**：正文、表格、附注、图表和前后章节的同一事实一致。
3. **交叉一致**：问询函、报告书、审定报表、附注、备考报告、评估说明和法律意见书的同口径对位。
4. **表述与文字**：结论与数据、名称、定义、单位、日期、标点和逻辑关系一致。
5. **问-答与披露**：监管问题被逐项回应，披露内容完整，法规和事实基础正确。

## 四、来源层级

外部来源默认按以下层级判断。层级只表达来源权威性，不替代具体证据核验。

| 层级 | 来源 |
|---|---|
| `AUTHORITY` | 法律法规、监管规则、监管/交易所正式公告、法院/政府官方记录 |
| `OFFICIAL` | 公司公告、年报、招股书、官网单篇披露、官方 IR |
| `PROFESSIONAL` | 审计、评估、法律、券商研究或行业协会公开材料 |
| `MEDIA` | 有编辑责任的财经媒体或新闻来源 |
| `OTHER` | 搜索摘要、聚合页、无来源转述、无法确认主体的网页 |

约束：

- 搜索结果摘要、列表页和首页不能单独作为事实证据；
- 优先使用直接内容页、公告 PDF 或官方数据库；
- 每个外部来源记录标题、发布主体、发布日期、访问日期、URL 或文件定位；
- 关键事实尽可能使用独立来源交叉验证；
- 来源冲突时保留双方，不自行选择"看起来更合理"的一侧。

## 五、数据截止日和时效

- 所有外部核查必须记录 `data_cutoff` 和 `source_access_date`；
- 报告中出现的"最新""截至目前"必须相对于数据截止日解释；
- 报告发布后发生的后续事件不得倒推修改报告期结论，除非作为复核更新单列；
- 来源后续更新时保留原结论、原日期和变更说明，不静默覆盖旧记录。

## 六、初始范围分类

在正式复核前把输入分为：

- `primary`：主审文件；
- `comparison`：同批其他申报文件；
- `working_paper`：计算或原始证据；
- `prior_version`：上期版本；
- `external_source`：外部核验来源；
- `context_only`：只用于理解业务，不作为权威值。

同一文件只能有一个主角色；如同时承担多个角色，记录全部角色和适用检查。

**问询回复类文件**按审核阶段包括：首轮问询回复、审核中心意见落实函回复、上市委审议意见回复、注册环节反馈回复，以及问询回复修订说明（补充披露对照表）。修订说明同时承担"变动索引"角色，必须纳入跨文件对碰与补充披露反向对碰（见 `cross-file-check.md` 第 10 节）。

## 七、降级与未覆盖

以下情况必须记录：

- 文件损坏、加密、无文本层或无法解析；
- 底稿缺失、公式无缓存值或权限不足；
- 外部 MCP、网页或模型不可用；
- 用户要求只查某个专项；
- 因上下文或性能限制跳过表格、章节或来源。

统一状态：

- `COMPLETE`：已按要求检查完成；
- `PARTIAL`：部分完成并已列明缺口；
- `NOT_RUN`：本轮未执行；
- `UNVERIFIABLE`：缺少必要证据，无法形成结论；
- `NOT_IN_SCOPE`：明确排除且已由用户确认。

任何降级都不得写成"未发现问题"。范围卡和覆盖状态应写入 Excel 总览页和交付说明。

## 八、精度与容差

统一口径：

- **同一数值直接对碰**：默认容差 `0.011` 万元；若差异只来自显示精度，记录为尾差说明，不升级为错误。
- **多项已舍入分项相加**：默认可解释尾差上限为 `0.05` 万元；超过后仍需回原始未舍入数据复算。
- **百分比**：默认可解释尾差上限为 `0.01` 个百分点，但必须先确认分母相同。
- **用户或项目底稿另有明确容差**：以用户确认为准，并写入 manifest。

不得通过放宽容差来"消除"实质差异。容差只用于显示精度和四舍五入，不用于掩盖口径差异、旧值残留或主体错配。

## 九、七方交叉与执行痕迹

默认要求的同口径交叉关系为：

`问询函（含审核中心意见落实函、上市委审议意见、注册环节反馈等后续审核文件）↔ 重组报告书 ↔ 审定报表 ↔ 财务报表附注 ↔ 备考审阅报告 ↔ 评估说明 ↔ 法律意见书/补充法律意见书`。

实际项目的文件角色和可得性不同，但每一条关键 claim 必须说明：

- 是否已找到同口径对照；
- 对照文件和位置；
- 未对位的原因；
- 当前状态是 `COMPLETE/PARTIAL/NOT_RUN/UNVERIFIABLE/NOT_IN_SCOPE`。

执行痕迹至少记录：

- 检查项数量；
- 命中候选数量；
- 确认问题数量；
- 跳过或降级数量；
- 开始和结束时间；
- 所用脚本、模型或工具版本；
- 中间产物文件名。

用户要求"过程回放"时，应能提供 `manifest.json`、`evidence-ledger.json`、`findings.jsonl`、覆盖表和中间检查结果。不得用抽样结果冒充全量结果。
