# 元审计：审计复核结果本身

> 元审计是在主复核完成后，对"是否真的查全、是否误报、状态是否准确、报告和批注是否一致"进行的第二层审计。它不等于简单重跑脚本，也不允许主 Agent 自审自过。

## 一、何时执行

`full` 和正式交付前必须执行。`continuation` 至少对原 A 级问题和新增问题执行。`quick` 或专项任务可缩小范围，但必须在交付说明中标记"未执行完整元审计"。

前置条件：

- `manifest.json`、`evidence-ledger.json`、`findings.jsonl` 已生成；
- 所有适用检查已完成或明确记录未执行；
- 原件哈希已记录；
- Excel 问题清单草稿已生成；
- Word 批注版草稿已生成或已完成锚点预检。

## 二、审计者独立性

优先使用全新上下文的独立 Agent。独立审计者必须：

1. 直接读取原始文件、底稿和来源，不只看主 Agent 摘要；
2. 不知道主 Agent希望的结论，也不以"报告已经写好了"为前提；
3. 使用同一 manifest、evidence schema 和 finding schema；
4. 独立判断 PASS/FAIL 和需要退回的 finding；
5. 不因主 Agent 已复核就降低验证标准。

若环境不支持独立 Agent，主 Agent按审计者角色重做，并在交付物明确写"未取得真正独立复核"。不得升级为 PASS 后再自行背书。

无法取得真正独立复核时的兜底交付：将全部 A 级 `CONFIRMED` finding 的证据包（原文片段、权威来源摘录、复算式、三项反证记录）单独导出为 `a-level-evidence-pack.md`（或 xlsx），随交付物一并提供，供项目组或内核人工抽查；导出路径记入 `meta-audit.json` 的 `notes` 字段。

## 三、A 级问题的三项反证

每个 A 级 `CONFIRMED` finding 至少尝试三项反证，并在 `counter_arguments` 中记录结果。不得只写"已检查"。

优先检查：

1. 单位或量纲：元/万元、百分比/百分点、股/万股；
2. 主体或范围：上市公司/标的公司/子公司、合并/母公司、备考/实际；
3. 期间或口径：报告期/最近一期、累计/单季、时点/期间、实际/预测；
4. 计算结构：负数、红字冲回、加减关系、分类小计、两层合计；
5. 表格结构：gridSpan、vMerge、合计行跨列、列错位；
6. 来源和版本：发布日期、数据截止日、权威底稿版本、期后更新。

三项反证全部失败后仍成立，才保留为 A 级 `CONFIRMED`。若任一反证成立：

- 可解释 → 降为 `PASS` 或写入口径差异；
- 无法解释 → 降为 `CANDIDATE`，记录待核事项；
- 来源不足 → 改为 `UNVERIFIABLE`。

## 四、审计主复核过程

### 1. 零发现检查

对每个章节、表格组或专项检查：

- 是真正完成且无异常，还是规则未执行？
- 是否有数据被截断、表格解析失败、图片/文本未提取？
- 是否因为上下文限制只做了抽样？
- 是否存在"所有问题都被判为口径差异"的异常宽松？
- 是否把 `NOT_RUN` 误写成 `PASS`？

### 2. 规则执行检查

核对：

- 该任务模式要求的 references 是否已读取；
- 表格是否全部进入验算或记录跳过原因；
- 关键 claim 是否进入 evidence ledger；
- 外部 claim 是否记录来源、日期和反证；
- 加期任务是否执行旧值、新周期和变动列检查；
- 问询任务是否执行结构对应和事实基础检查。

### 3. 候选升级检查

抽查并验证：

- `CONFIRMED` 是否真的有原始载体证据；
- `CANDIDATE` 是否被错误写成确定错误；
- 是否将重复披露本身列为错误、候选或整改建议，或仅以“相互引证”为由建议避免重复；如有，移出问题清单及对应批注。多处披露的具体不一致应保留，但须明确不一致内容和证据，不以重复披露定性；“重大风险提示”与“风险因素”是否满足筛选及层次要求，须按 `rule26-checklist.md` 单独核验，不能因一般重复披露排除规则而跳过；
- `UNVERIFIABLE` 是否有具体缺口；
- `PASS` 是否有实际核验记录；
- `NOT_IN_SCOPE` 是否经用户确认。

### 4. 报告一致性检查

确认：

- finding 数量与 Excel 问题清单一致；
- Word 批注数量和锚点与 Excel 逐条对应；
- manifest、ledger、findings ID 互相引用正确；
- 报告修改时间不晚于复核结论时间；
- 复核结论变更后，Excel 和 Word 已重新生成；
- 没有 finding 在批注版中被遗漏或重复。

### 5. 载体覆盖审计（防"结构性盲区"）

问题条数不构成覆盖完整性的证明。必须按载体拆开，逐类确认：

1. **图**：`word/media` 是否已全量导出？每张图的所属章节是否已定位？承载实质披露的图（结构图／关系图／示意图／流程图／股权结构／产权控制关系／组织架构）是否已逐张识读并纳入比对？未识读的是否逐张说明了理由？
2. **表格**：是否全部进入验算或记录跳过原因？
3. **正文段落**：数值索引是否覆盖正文中的数值（不只表格）？
4. **表下注释**：是否做过逻辑比对（不只错别字扫描）？
5. **目录**：是否与正文标题、图标题做过双向比对？
6. **跨载体矩阵**：同一主体、比例、金额是否在五类载体之间交叉比对过？是否只做了同类载体互比？
7. **判据回源**：本次针对图形载体出的每条 finding，其所依据的"应当披露什么、披露到什么程度"是否已回源到规则原文（准则条款）？有没有用自设标准当判据？**凡未回源判据即定性的图形类 finding，一律退回重判。**

审计者须输出一张**载体覆盖矩阵**（载体 × `COVERED`／`PARTIAL`／`NOT_RUN`／`NOT_IN_SCOPE`），随交付物提供。

**判定要点**：

- 交付物限制栏中出现"图片未纳入""图表未覆盖"等表述，而该文件中确有承载实质披露的图，且技术上可提取识读的 → 属于**未执行**而非限制，元审计不得 PASS。
- **误报与漏报同责**。图内数字类 finding 若未做过放大逐字符复核，或结构图类 finding 未回源判据，即存在误报风险；已知的误报须在交付物中明确撤回并说明更正，不得静默删除。**"清单条数多"不是质量证明，"误报少"才是项目组愿意用它的理由。**

### 6. 内部引用核验

确认“参见”“详见”等引用已逐条核对正文目标的存在性、完整层级路径、编号及标题名称，并读取目标内容检验是否承接所引事项。不得只核查目录、标题或关键词命中；章节改版后的关联引用须回查。断链、循环、目标内容不符和无法读取的情形须分别记录。方法见 `text-errors.md`。

## 五、问题签名和重复发现

对 finding 计算问题签名，建议使用：

`任务维度 / 主体 / 指标或事项 / 期间 / 口径 / 根因`

例如：

`cross_file/add_period/归母净利润/2026H1/同口径/旧值未同步`

用途：

- 同签名问题跨文件重复出现时合并或建立关联；
- 重复出现在多个项目的模式，回写 `common-errors.md`；
- 反复出现于同一模板的，提示模板或流程缺陷；
- 不因签名相同就自动合并，仍要核对主体、期间和具体证据。

## 六、元审计结论

建议生成 `meta-audit.json`：

```json
{
  "audit_id": "MA-0001",
  "created_at": "2026-09-25T10:00:00+08:00",
  "scope_complete": true,
  "findings_reviewed": 42,
  "a_confirmed_reviewed": 6,
  "counter_evidence_complete": true,
  "coverage_issues": [],
  "downgraded_findings": [],
  "new_findings": [],
  "report_findings_consistent": true,
  "comment_findings_consistent": true,
  "verdict": "PASS",
  "notes": ""
}
```

`verdict`：

- `PASS`：可以进入交付；
- `FAIL`：退回修订，明确退回项；
- `PARTIAL`：只有非关键缺口，交付前逐项披露；
- `BLOCKED`：缺少关键文件、权限或来源，无法完成元审计。

## 七、元审计失败处理

出现以下情况之一即为 `FAIL`：

- A 级问题证据不足；
- 报告和 finding 数量不一致；
- 批注锚点无法回源；
- 关键表格未执行也未记录；
- 候选被写成确认错误；
- 来源冲突未经决策就选边；
- 复核后文件被修改但结论未更新；
- 无法说明任何一项"零发现"的覆盖依据；
- **存在承载实质披露的图形载体未提取、未识读，且未说明理由**；
- **交付物中残留"能消除却未消除"的覆盖限制**（如以"解析能力不足"为由整体排除图片）；
- **未提供按载体的覆盖矩阵**，或矩阵中存在 `NOT_RUN` 载体而未在交付说明中逐项披露；
- **图形类 finding 未回源披露判据**（用自设的"完整性直觉"当标准，如要求结构图列全股东名册）；
- **图内数字类 finding 未经放大逐字符复核**，存在识读误判风险。

处理顺序：

1. 退回 finding，重新核证或降级；
2. 更新 ledger、Excel、Word 和 manifest；
3. 重新运行相关检查；
4. 再次元审计，直到 PASS 或明确 BLOCKED；
5. BLOCKED 时不得宣称完整复核。
