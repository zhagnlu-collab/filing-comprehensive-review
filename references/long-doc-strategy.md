# 长文档分段复核策略

> 报告书和问询回复全本可能超出单次上下文窗口。是否算"长文档"不写死字符数，按运行环境实际窗口判定：
>
> **长文档阈值（参数化）**：安全装载量 ≈ 实际上下文窗口 token 数 × 60%（预留 40% 给检查规则、权威值集合、问题清单和输出）。中文字符按 1 字符 ≈ 1 token 保守换算。示例：128k token 窗口 → 安全线约 7.7 万 token，即约 7–8 万中文字符；1M token 窗口 → 约 60 万中文字符。文档超出安全装载量即按长文档处理；拿不准窗口大小时按保守估计（历史默认值：10 万字符以下视为短文档、40 万字符以上视为长文档）。

## 一、长文档与短文档复核的区别

| 维度 | 短文档（安全装载量以内） | 长文档（超安全装载量） |
|------|---------------------|---------------------|
| 上下文压力 | 单次可装全文 | 需分段处理 |
| 复核方式 | 可"通读+程序化" | 必须"程序化优先 + 分段语义" |
| 表格数量 | 少，可全量验算 | 多，需优先级排序 |
| 跨文件对碰 | 全量数值对碰 | 需按章节/问题聚焦 |
| 断点续作 | 不需要 | 必须支持中断后继续 |

## 二、分层分段策略（推荐工作流）

### 第 1 层：程序化核对（不依赖上下文，覆盖 ~70% 工作）

全部脚本化执行，不需要逐段阅读：

| 检查项 | 方法 | 工具/脚本 |
|--------|------|----------|
| 表格勾稽 | 合计=分项和、率×基数、完成率、增长率 | table-arithmetic.md 验算脚本 |
| 期数列检测 | 财务数据表缺 2026H1 列 | extension-review.md 期数列检测 |
| 旧值残留 | 新值/旧值 grep 全文件 | cross-file-check.md 旧值残留检测 |
| 跨文件对碰 | 数值索引 + grep（facts.jsonl） | `cross-file-check.md` |
| 定性事实对碰 | 定性事实索引 + 跨章比对（qualitative-facts.jsonl，见下） | 本文件「三、上下文窗口管理技巧」第 2 条 |
| 文字表述错误 | 和字连接/叠词/半角逗号/文号括号/其它 | text-errors.md 正则扫描 |
| 格式一致性 | 全角/半角、单位、日期格式 | format-consistency.md |

> **数值索引必须覆盖正文文字中的数值，不能只从表格构建**："本次交易作价为 X 亿元""发行股份 Y 万股"这类句子里的数值若不入索引，跨章对碰就会形成盲区。分段复核时顺手抽取本章正文数值补入 facts.jsonl（格式同表格数值，locator 记"章节+句首 10 字"）。

### 第 2 层：按章节/问题分段语义复核（仅对需要理解的章节）

| 步骤 | 内容 |
|------|------|
| 章节划分 | 重组报告书按 18 章；问询回复按 10 个问题 |
| 优先级排序 | 财务数据密集章节（第九章管理层讨论与分析、第十章财务会计信息、问题三/五/六/七）> 定性章节（第一/二/七/八章、问题一/二/四/八/十） |
| 每章独立复核 | 表外一致（正文 vs 表格）+ 结论与数据矛盾 + 口径混用 + 本章跨文件对碰 |
| 上下文管理 | 每章完成后清空上下文，仅保留本章问题清单和权威值集合 |

> **最低检查集（硬规则，所有章节无一例外）**：优先级排序只降"语义复核深度"，不降"程序化覆盖"。每章（含低优先级定性章节）必须完成：①第 1 层全部检查项对本章范围全量执行；②本章表外一致核对；③本章正文数值与定性事实抽取入索引。未完成最低检查集的章节，覆盖状态不得记 COMPLETE。

### 第 3 层：合并与根因定性

| 步骤 | 内容 |
|------|------|
| 合并问题清单 | 各章问题清单合并为总清单，按等级（A/跨文件/B/C）排序 |
| 差额同源分析 | 检查多个差异的差额是否相同或关联（如 96.12 串联四个文件），锁定同一根因 |
| 根因定性 | "沿用加期前数据"/"加期更新不同步"/"口径未披露"/"四舍五入尾差"等 |

## 三、上下文窗口管理技巧

1. **权威值集合外置**：审定报表/附注/备考审阅报告的关键数值提前抽取为结构化数据（JSON/CSV），复核时按需查询而非全文加载：
   ```json
   {"合并利润表": {"2026H1": {"营业收入": 2073967319.27, "归母净利润": 210084260.07, "投资收益": 157039468.68}}}
   ```
2. **定性事实索引外置**（qualitative-facts.jsonl）：权威值集合只装数值，装不下"定性事实"；分段清空上下文后，跨章定性口径无人核对，必须另建索引。抽取对象至少包括：
   - 控制权/实控人认定表述（如"本次交易前后实际控制人均为×××"）；
   - 承诺事项（业绩承诺、锁定期承诺、避免同业竞争承诺等，逐条建行，供"承诺→履行情况"闭环核对）；
   - 口径定义（报告期、审计截止日、评估基准日、加期安排、指标口径如"扣非前后孰低"）；
   - 关键日期与关键比例（签约日、交割日、停牌日、持股比例、占比阈值）；
   - 主体全称清单（上市公司、标的公司、交易对方及其曾用名/简称映射）。

   分段复核时每章顺手抽取，格式一行一条：
   ```json
   {"fact_type": "控制权认定", "subject": "实际控制人", "statement": "本次交易前后实际控制人均为张某", "normalized_value": "张某", "locator": "第一章/二/(三)/段首「本次交易完成后」"}
   ```
   第 3 层合并时按 `fact_type + subject` 跨章去重比对：`normalized_value` 不一致即候选问题；承诺事项另与"履行情况"章节逐条闭环。未建定性事实索引的长文档项目，元审计时按"跨章定性口径未核对"标记，不得整体记 COMPLETE。
3. **增量加载**：只把"当前复核的章节文本 + 权威值集合 + 检查规则"放入上下文；
4. **断点续作**：用 `manifest.json` 记录各章节复核进度（已完成章节/当前章节/待复核章节），支持中断后从断点继续：
   ```json
   {"M2": {"chapters_done": ["第一章","第二章"], "current": "第三章", "pending": ["第四章",...,"第十八章"]}}
   ```

## 四、子代理并行（若环境支持 Agent spawn）

若环境支持 Agent spawn（如 HAB/WorkBuddy/Codex 平台）：
- 每个章节/问题 spawn 一个子代理并行复核，主代理合并结果；
- 子代理间用统一的问题清单 schema（等级/编号/文件名/问题描述/位置/原文/应更新为/说明）；
- 主代理负责：权威值集合分发、结果合并、差额同源分析、二次复核。

若环境不支持 Agent spawn：
- 主代理按章节顺序复核，每章完成后清空上下文，只保留问题清单和权威值集合。

## 五、长文档复核常见陷阱

1. **不要试图"通读全文"**：40 万字符的文档逐段通读会耗尽上下文且效率低，必须用程序化核对覆盖大部分工作；
2. **不要忽略"变动列未同步"**：加期插入新列后，"余额变动"列未同步是典型漏更新（借自问题七表 32）；
3. **不要只做"本章勾稽"不做"跨章对碰"**：同一指标在不同章节（如第九章 vs 第十章）可能不一致，需跨章对碰；
4. **不要忽略"差额同源"**：多个章节的差额若相同，往往指向同一根因（同一批未同步数据），合并标注可大幅提高问题定位效率；
5. **不要忘记断点续作**：长文档复核可能分多次会话，manifest.json 必须记录进度；
6. **不要只索引表格数值**：正文句子里的数值（"作价为 X 亿元""发行 Y 万股"）不入索引，跨章对碰就会漏掉第九章与第十章各说一个数的情形；
7. **不要只对数值、不对定性事实**：控制权认定、承诺事项、口径定义跨章不一致，是分段清空上下文后最典型的漏检，必须靠定性事实索引对碰兜底；
8. **不要给低优先级章节"跳章"待遇**：语义复核可以降权，最低检查集（第 1 层全部检查项＋表外一致＋索引抽取）一章都不能少。

## 六、元审计与子代理约束

长文档的分段结果不能直接合并后交付。每轮分段复核后必须执行 `meta-audit.md`：

- 独立子代理必须直接读取原始章节和底稿，不得只看主代理摘要；
- 每章记录 `COMPLETE/PARTIAL/NOT_RUN/UNVERIFIABLE/NOT_IN_SCOPE`；
- 对零发现章节检查规则是否实际执行、表格是否完整解析、上下文是否被截断；
- 对 A 级确认问题至少完成三项反证；
- 合并后检查同一问题签名是否重复、是否存在前后章节口径冲突；
- 发现权限、工具或文件损坏导致的中断时，保留断点并如实标记，不得把未完成章节写成通过。

修订后的每轮续核按 `re-review.md` 执行，逐条检查原问题闭环、旧值清零、新值同步和回归错误。
