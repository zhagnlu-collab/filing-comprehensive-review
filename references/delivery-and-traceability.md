# 溯源交付与最终门禁

> 交付必须让用户能从问题清单直接回到原文，也能看到权威来源、复算过程和当前证据状态。找不到原文、来源或证据的记录，不得进入正式问题清单。

## 一、交付物

面向用户的交付物仅为三种：

1. **Excel 问题清单**：结构化问题、等级、证据状态、原文定位、依据、复算及建议；续核所需的闭环、旧值清零、新值同步、回归和未决事项放入同一工作簿。
2. **Word 批注版**：在原件副本中逐条锚定问题，保留既有批注及修订，区分已确认问题与候选事项。
3. **HTML 文件**：包含结论、重点问题、范围、文件版本、核查依据、按章节及载体的覆盖矩阵、未执行事项、限制、元审计结论及续核统计；可在浏览器直接打开，所需内容内嵌，无需另行交付数据文件。

范围卡、证据台账、结构化问题和元审计记录（`manifest.json`、`evidence-ledger.json`、`findings.jsonl`、`meta-audit.json`）及校验日志保存在内部工作目录，继续用于追溯、续核与脚本校验，不单独交付。覆盖说明、证据包、续核闭环和回归检查均纳入上述 Excel 或 HTML，不增加 JSON、JSONL、Markdown 或其他报告附件。

三种文件的问题编号、影响等级、证据状态和统计口径必须一致。HTML 中直接呈现关键依据、原文摘录与来源定位，不得仅链接内部记录。缺少 Excel、Word 或 HTML 任一种时，必须说明阻断原因、影响文件和未覆盖范围，不得静默降级或声称完整交付。

## 二、Excel 问题清单字段

建议至少包含：

| 列 | 内容 |
|---|---|
| 序号 | `FND-` 问题编号 |
| 影响等级 | A/B/C |
| 证据状态 | CONFIRMED/CANDIDATE/PASS/UNVERIFIABLE/NOT_IN_SCOPE |
| 问题类型 | 与 error taxonomy 一致 |
| 文件名简称 | 用户可识别的自然名称 |
| 位置 | 章节/小标题/表名/页码/单元格 |
| 原文 | 文件中真实存在的原文片段 |
| 权威值/预期值 | 正确值或应存在的表述 |
| 实际值 | 实际披露值 |
| 差异/勾稽式 | 差额、公式或证据关系 |
| 根因 | 旧值、口径、错位、漏更新、来源不足等 |
| 修订建议 | 最小可执行修改 |
| 连带影响 | 其他文件和章节 |
| 责任方 | 券商/律师/会计师/评估师/标的公司/项目组（问题清单按责任方流转） |
| 预沟通状态 | A 级必填：已预沟通/未预沟通及原因 |
| 证据 ID | `EVD-` 或来源清单 |
| 复核对状态 | OPEN/FIXED/PARTIAL/NOT_FIXED/REGRESSION |
| 备注 | 口径、限制和人工待决 |

字段可在 Excel 中分工作表展示，但不得用内部代号替代用户可识别位置。

## 三、定位规则

### 1. 文件名

使用用户能识别的简称，不用 `M1`、`C1`、`P1` 等内部代号。

### 2. 位置

优先使用：

`文件名简称 + 实际章节名 + 小标题 + 表名或原文前 15 个字`

例如：

`清洁版问询回复/问题九/（三）主要合营联营企业经营情况/东实李尔及东实李尔（武汉）主要从事汽车座椅研发、生产和销售`

禁止把"表 79""段 2669""R24""X01"作为唯一定位。它们可以作为辅助记录，但必须同时提供用户可搜索的原文锚点。

### 3. 原文

- 必须是 Word、Excel 或原始来源中真实存在的片段；
- 不得写摘要、推测或"问题九：某指标不一致"之类的转述；
- 复算值、建议值应标注"复算"或"建议"，与原文区分；
- 原文片段要足够独特，确保用户复制后能 Ctrl+F 或页面搜索定位；
- 表格数字须保留期间、单位、口径和实际/预测属性。

### 4. 外部来源

记录：

- 来源标题和发布主体；
- 直接内容 URL 或文件名；
- 页码、章节、单元格或字段；
- 发布日期和访问日期；
- 原文摘录；
- 层级和独立性说明。

## 四、证据状态措辞

- `CONFIRMED`：请改为……；已回权威来源或原始载体确认。
- `CANDIDATE`：请核实……；当前为候选异常，尚未确认。
- `PASS`：已核对一致；记录勾稽式或检查范围。
- `UNVERIFIABLE`：本次无法核验；写明缺少的证据和已尝试渠道。
- `NOT_IN_SCOPE`：本次未纳入范围；写明原因和用户确认依据。

禁止把 `CANDIDATE` 写成"错误"，把 `UNVERIFIABLE` 写成"通过"，把 `NOT_RUN` 写成"零问题"。

## 五、已核对一致留痕

除问题外，还应在 Excel 或 HTML 中保留正向留痕：

- 已完成的勾稽式；
- 已核对的权威来源；
- 已检查且一致的跨文件数据；
- 已确认不适用的事项；
- 已检查的表格和章节数量；
- 无法覆盖内容的明确原因。

留痕不是简单写"已检查"，要包含关键数值、范围或检查依据，便于用户抽查。

## 六、原件保护

- 原件只读；
- 批注版另存副本；
- 记录原件复核前后 SHA-256；
- 不移动、不删除、不覆盖原件；
- 若用户要求生成修订版，另行确认并单独输出，不覆盖原件。

## 七、最终门禁

交付前逐项确认：

1. 范围、角色、版本和截止日已固化；
2. 全部关键表格已验算或记录未执行原因；
3. 全部关键 claim 已进入 evidence ledger；
4. 跨文件关键数据点已对碰或记录未对位原因；
5. 每个 A 级 CONFIRMED 问题有三项反证记录；
6. 外部事实有来源、日期、原始摘录和正确处理；
7. `CONFIRMED / CANDIDATE / PASS / UNVERIFIABLE / NOT_IN_SCOPE` 状态准确；
8. finding 与 Excel、Word 新增批注、HTML 的问题及统计口径一致，既有批注另行区分；
9. 每条批注锚定文本真实存在；
10. 原件 SHA-256 复核前后一致；
11. 元审计 PASS 或明确披露 PARTIAL/BLOCKED；
12. HTML 已列出覆盖矩阵、限制、未执行事项、降级原因及元审计结论，用户交付仅含 Excel 问题清单、Word 批注版和 HTML 文件；
13. manifest、ledger、findings 和交付文件版本一致；
14. `scripts/validate_review_artifacts.py` 已运行通过，或逐项说明失败原因；
15. A 级问题已在正式交付前与项目组预沟通，或在交付说明中逐项列明未预沟通的 A 级问题及原因。

## 八、复核结论表述

结论应先回答：

- 本次是否在已声明范围内完成；
- 是否存在 A 级问题；
- 是否有未核验或无法核验事项；
- 是否允许进入下一轮修订或提交；
- 下一步需要谁决策。

不得用"看起来没问题""整体质量较高"替代覆盖结论。存在 `PARTIAL`、`UNVERIFIABLE` 或 `BLOCKED` 时，必须醒目披露。
